## 2. 实施纪律

1. 按 P0、P1、P2 顺序修正；P0 未全部通过时不得处理真实群 canary。
2. 不通过改名为 `.skip`、添加宽泛白名单、删除失败断言或硬编码返回值规避测试。
3. 每个修正先恢复或增加失败测试，再实现真实行为。
4. 一次只提交一个紧密问题组；每个提交必须包含定向测试结果。
5. 不宣称某项 PASS，除非对应命令在当前提交上真实通过。
6. Worker 只负责同步、匹配、聚合和规划持久化任务，不连接 QQ。
7. AstrBot 插件负责事件适配和消息发送，不在插件中重写数据源或领域规则。
8. PostgreSQL 是唯一业务事实来源；并发、租约和迁移测试不得用 SQLite 替代。

## 9. P0：实现真实通知投递

当前 dispatcher 只渲染并标记 sent，必须重写。

### 9.1 会话定位

- 根据 job 的 `chat_group_id` 查询最新 ChatGroup；
- 获取持久化 UMO；
- 缺少 UMO 时任务保持 pending/retryable，并提供可操作原因；
- 不允许根据群号猜测或拼接 UMO。

### 9.2 实际发送

使用 AstrBot 主动消息接口：

```python
await context.send_message(unified_msg_origin, message_chain)
```

参考：[AstrBot 主动消息文档](https://docs.astrbot.app/dev/star/guides/send-message.html)。

MessageChain 必须支持：

- `At` 匹配用户；
- `Plain` 通知内容；
- airing 的“预计放送”措辞；
- Mikan 的资源摘要和页面链接。

### 9.3 投递结果

- 只有发送 API 明确成功后标记 sent；
- retryable 按退避重新 pending；
- permanent 标记 failed；
- 请求结果不确定标记 unknown，不能盲目重发；
- airing 超过 2 小时 expired；
- Mikan 超过 24 小时 expired；
- DeliveryAttempt 保存真实 attempt number 和脱敏结果。

### 9.4 测试

Fake Context 测试必须断言：

- `send_message()` 被调用；
- 参数使用数据库 UMO；
- MessageChain 含预期 At；
- 发送失败不能标记 sent；
- 插件重启后租约恢复；
- 两个 consumer 不重复 claim。

## 10. P0：完成 Mikan 流水线

### 10.1 RSS 安全与条件请求

- 使用安全 XML parser，禁止外部实体和实体扩展；
- 实现 ETag、Last-Modified 和 304；
- 保存每个 feed 的同步状态和错误；
- 不接受用户 token；
- 不保存和发送磁力或下载直链。

### 10.2 按订阅轮询

- 只轮询资源提醒开启的 Follow Subscription；
- 必须具有 confirmed Mikan Source Link；
- blocked Anime 不轮询；
- 多个群订阅同一 Mikan Anime 时 feed 只轮询一次；
- 设置全局并发、抖动、超时和退避。

### 10.3 Release 持久化

- GUID 去重；
- 页面链接和规范化内容指纹辅助去重；
- 保存原始标题和 parser version；
- 未确认映射或无法解析集数时保存但不提醒；
- ingestion 与 batch 打开在事务中完成。

### 10.4 真实用户筛选

实现：

- 简体、繁体和不限；
- 一个或多个字幕组；
- 一个或多个分辨率；
- unknown 只在用户选择不限时匹配；
- 不得继续使用 `return releases[:5]` 作为筛选。

### 10.5 持久 Release Batch

- 同 Anime、episode key 首次 release 打开 10 分钟窗口；
- 后续 release 加入同一窗口；
- batch 状态和窗口存 PostgreSQL；
- Worker 重启后继续关闭到期 batch；
- 每群生成一个稳定 dedupe job；
- 无用户匹配时 suppressed；
- 单条消息最多展示 5 条，其余显示数量。
