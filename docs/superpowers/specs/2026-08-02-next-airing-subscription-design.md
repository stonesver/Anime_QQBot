# 订阅当前下一集与完结番剧保护设计

日期：2026-08-02  
状态：已确认，待实现

## 1. 目标

“订阅番剧”的产品语义是订阅当前阶段的下一集开播，而不是回放已经发生的集数。资源提醒继续服务于未完结番剧；已确认完结的番剧不创建订阅，也不发送开播或资源提醒。

本设计解决以下问题：

- 订阅时数据库已经有多集历史播出记录，不为历史集数补发通知；
- 播出记录延迟同步或批量补同步时，不连续追发多集；
- 同一集有 Bangumi/AniList 多来源记录时，不生成重复任务；
- Worker 已创建下一集待发送任务后，用户才订阅时，不漏掉该用户；
- 无法确认完结时，不因缺少下一集数据误判完结；
- 已确认完结时，不留下会被资源同步误触发的订阅。

## 2. 已确认的业务规则

### 2.1 订阅类型

- 未完结且存在未来精确播出时间：创建订阅，开启开播提醒和资源提醒。
- 未完结但没有未来精确播出时间：创建订阅，保留资源提醒；开播提醒等待后续同步到新的精确时间。
- 已确认完结：不创建 `follow_subscriptions`，返回说明“已完结，无需订阅”，不发送任何提醒。

资源提醒不改变现有的 Mikan 聚合、资源筛选、Outbox 和低噪声策略；完结番剧因为不创建订阅，自然不会进入资源同步提醒受众。

### 2.2 历史与下一集

- 订阅基线使用现有 `FollowSubscription.created_at`。
- `air_at < now` 的 Airing Occurrence 一律视为历史，不生成新的开播任务；即使仍在原有延迟补偿窗口内，也不补发。
- Worker 每轮对每部 Anime 只选择最早的未来精确 Airing Occurrence 作为当前下一集。
- 日期级记录只能用于查询展示，不能直接生成开播提醒；同一集的精确来源优先于日期级来源。
- 同一群、Anime、集数继续使用 `airing/{anime_id}/{episode_label}` 作为通知业务键。

### 2.3 待发送任务竞态

如果某一集尚未播出、对应 airing job 状态仍为 `pending`，用户在此时订阅：

- 将用户加入该群该 job 的 `at_user_ids`；
- 该操作必须幂等，不能重复追加同一用户；
- job 已到点、已租约或已发送后不再改写受众；
- 只更新当前最早的未来 airing job，不把用户加入更远期的多个任务。

如果用户在该集 `air_at` 之后才订阅，则不加入该集任务。

## 3. 完结判定

完结判定采取保守策略。只有满足以下任一条件才判定完结：

1. 可信来源快照明确提供完结状态；
2. 已知 `total_episodes > 0`，且已播集数达到该总集数。

仅仅“当前没有未来播出记录”不能判定完结。缺少状态、总集数或播出记录不完整时，按“未完结但下一集时间暂未同步”处理，继续保留订阅和资源提醒。

订阅反馈应区分：

- 有下一集：说明当前已播集数和下一集时间；
- 无下一集但未确认完结：说明等待后续同步；
- 已确认完结：说明无需订阅且不会发送提醒。

## 4. 组件与数据流

### 4.1 订阅用例

`subscribe()` 在写入订阅前调用 Anime Core 的状态判定：

1. 读取 confirmed source snapshots 和 Airing Occurrence；
2. 判定完结、当前已播集数和未来最早精确下一集；
3. 已完结时直接返回，不写订阅；
4. 其他情况写入现有订阅；
5. 对未来 pending airing job 做一次幂等受众补写；
6. 返回订阅结果与状态说明；
7. 继续按现有流程异步请求订阅后的来源补充，不在消息路径访问外部数据源。

### 4.2 Worker 与 Outbox

Worker 的开播规划只查询未来精确 occurrence，并按 Anime 选择最早一条。`AiringPlanner` 负责按群聚合订阅用户、写入唯一 airing job；Outbox 负责并发安全和持久化。

受众补写放在 Outbox repository 的事务边界内：锁定匹配的 pending job，读取现有 `at_user_ids`，集合并入新用户后提交。不存在匹配 job、job 已非 pending 或播出时间已过时返回幂等的 no-op。

### 4.3 查询与展示

详情/订阅响应可以显示当前已播集数、下一集和数据状态，但不得把资源发布与播出事件混为一谈。查询失败或状态字段缺失时返回保守的“下一集时间暂未同步”，不自动判定完结。

## 5. 错误与兼容性

- 上游同步失败不删除订阅，也不把未知状态改成完结。
- 多来源 occurrence 仍保留在目录中；展示和开播规划按精度去重，不能直接删除来源记录。
- 现有已发送任务不回溯修改；部署时可单独清理已经过期的历史 pending airing job，但不影响资源任务。
- 现有 `notify_resource` 过滤规则、Mikan 聚合窗口、SendGovernor、静默时段和断路器保持不变。
- 重复订阅仍幂等；取消订阅仍删除当前用户当前群的订阅。

## 6. 验收与回归测试

必须覆盖：

- 已播 1–4 集、未来第 5 集：只规划第 5 集；
- 批量补同步历史集数：不产生历史 airing job；
- 同一 Anime 有多个未来 occurrence：只取最早一集；
- 同一集 Bangumi/AniList 多来源：只产生一个业务 job；
- pending job 创建后、播出前订阅：用户加入 `at_user_ids`；重复补写不重复；
- 播出后订阅：不加入已经发生的 job；
- 已确认完结：不创建订阅、不生成 airing/resource 提醒；
- 未确认完结且暂无下一集：创建订阅并等待，不误判完结；
- 资源筛选、聚合、Outbox 去重和现有订阅幂等测试继续通过。
