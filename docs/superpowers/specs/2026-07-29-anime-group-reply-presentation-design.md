# Anime QQBot 群聊回复与番剧卡片设计

## 状态

- 日期：2026-07-29
- 状态：已确认，实施计划已编写
- 实施计划：[群聊回复与番剧卡片实施计划](../plans/2026-07-29-anime-group-reply-presentation-implementation-plan.md)
- 接入边界：AstrBot + NapCat + 普通 QQ 小号
- 部署边界：2 核 2 GiB 服务器，保留现有静态站与 NapCat 发布隔离

## 1. 背景

项目已经支持群内番剧搜索、今日与本周放送、季度列表、订阅、开播提醒和 Mikan 更新
提醒，但大部分回复仍是连续纯文本。单番信息层级不明显，帮助和列表也缺少一致的扫读
结构。

本设计只处理群聊回复呈现。管理面板美化是独立子项目，不纳入本轮。此前
`2026-07-16-adaptive-qq-message-presentation-design.md` 面向已经移除的 QQ 官方机器人
Markdown 与按钮能力，不再作为当前 AstrBot/NapCat 运行时的实施依据。

## 2. 目标

- 为单番查询提供统一、易识别的“放送信号”图片卡片；
- 保持列表、订阅和主动提醒为快速、可复制的结构化文本；
- 群消息处理只读取 PostgreSQL 与本地文件，不等待外部数据源或远程图片；
- 真实海报不可用时直接返回等价文本，不使用占位图；
- 在 2 GiB 服务器上限制渲染并发、内存和磁盘占用；
- 保持业务用例、展示数据、图片生成和 AstrBot 消息组件相互隔离；
- 保持现有群聊防误触、候选会话、发送限频和通知规则不变。

## 3. 非目标

- 不恢复 QQ 官方机器人、QQ Markdown、官方按钮或 ARK 模板；
- 不把今天、本周、季度或我的订阅渲染成长图片；
- 不把订阅确认、错误、帮助、开播提醒或 Mikan 提醒改成图片；
- 不在群消息请求中下载海报、调用 Bangumi、AniList 或 Mikan；
- 不生成 AI 海报，不使用通用占位图；
- 不引入 Chromium、Playwright 截图服务、Redis 或新的常驻容器；
- 不建设独立对象存储或公网图片代理；
- 不改变查询、订阅、权限、候选编号和通知业务语义。

## 4. 回复策略

采用“轻量图文”策略。图片只用于单番且有真实海报的场景，其余场景使用结构化文本。

| 场景 | 默认载体 | 海报不可用时 |
| --- | --- | --- |
| 搜索唯一命中 | 放送信号卡片 | 等价结构化文本 |
| 番剧详情 | 放送信号卡片 | 等价结构化文本 |
| 下一集 | 放送信号卡片 | 等价结构化文本 |
| 搜索多个候选 | 带编号文本 | 不适用 |
| 今天、本周、季度 | 分组文本 | 不适用 |
| 我的订阅 | 紧凑文本 | 不适用 |
| 订阅、退订、订阅设置 | 状态文本 | 不适用 |
| 帮助、状态、映射、错误 | 文本 | 不适用 |
| 开播提醒、Mikan 更新 | 文本与必要的 `@` | 不适用 |

单番图片之后最多附一行可执行提示，例如 `追番 夏日物语`。提示不重复图片中的完整
字段。

## 5. 放送信号卡片

### 5.1 尺寸与布局

输出固定为 `1000 × 600` PNG，宽高比为 `5:3`。QQ 客户端按聊天区域自动缩放；手机端
约为普通横图大小，不按原始像素撑满屏。

卡片分为两栏：

- 左栏 `400 × 600`，固定为标准 `2:3` 真实海报；
- 右栏 `600 × 600`，显示标题、下一集和多源投影字段。

有效海报不是 `2:3` 时，使用同一张真实海报生成模糊铺底层，并将完整原图等比居中到
前景。不得拉伸原图，也不得用无关素材填充。图片缺失、下载失败、解码失败或超过安全
限制时，不生成卡片。

### 5.2 视觉身份

视觉方向为“放送信号”，来源于电视节目编排表，而不是通用数据面板。

| Token | 色值 | 用途 |
| --- | --- | --- |
| 节目纸 | `#F7FAFF` | 右侧卡片底色 |
| 信号蓝 | `#365FC7` | 放送时间轨与主要结构 |
| 开播红 | `#FF5D57` | `ON AIR` 状态 |
| 墨色 | `#17223B` | 主标题与正文 |
| 雾蓝 | `#E9EFFD` | 次要信息与时间轨底色 |

中文正文与标题使用镜像内固定且通过构建验收的 Noto Sans CJK 字体；时间、状态和来源
标签使用等宽字体。若基础镜像缺少可用 CJK 字体，Dockerfile 安装 Noto Sans CJK，并在
真实镜像构建中生成包含中日文的样卡验证。运行时不得猜测字体或依赖宿主机字体。

本设计唯一的强调元素是放送时间轨：时间使用信号蓝底和大号数字，日期、星期和集数
位于其右侧。其余装饰保持克制。

### 5.3 信息密度

卡片采用均衡密度，不显示简介。字段按以下顺序展示：

1. 年份、季度和可用的作品类型；
2. 中文或本地展示标题；
3. 可用的日文标题；
4. 下一集时刻、日期、星期和集数；
5. Bangumi 评分、总集数、放送状态；
6. 已确认的 Bangumi、AniList 和 Mikan 来源标签。

字段缺失时直接隐藏对应次要字段，不显示 `None`、空标签或伪造值。没有已知下一集时，
时间轨显示 `待定` 和 `暂无已知下一集`。所有时间转换到群设置时区；当前默认时区仍为
`Asia/Shanghai`。

NSFW 或被禁用作品继续由现有应用层阻止，不得进入卡片数据与图片渲染。

## 6. 文本回复

今天、本周和季度列表按日期或星期分组。每条只显示时间、标题和可用的集数；页尾最多
保留一句场景相关提示。

示例：

```text
🗓 本周放送 · 5 部

周二 · 07-30
18:00  夏日物语 · 第 4 集
21:30  异世界食堂 · 第 6 集

周五 · 08-02
20:00  银河旅人 · 第 3 集

追番时发送「追番 名称」
```

不依赖等宽中文字符绘制表格边框，避免不同 QQ 客户端字体造成错位。候选结果继续使用
短编号和五分钟会话，不暴露内部 UUID。

图片降级文本必须覆盖卡片的可用语义字段，包括标题、下一集、评分、总集数和来源状态；
它不是一句笼统的“图片加载失败”。

## 7. 模块边界

新增四个窄接口，不把图片逻辑继续堆入现有聊天适配器。

### 7.1 `CardDataAssembler`

输入 Anime ID、群时区和当前时刻，读取本地 PostgreSQL 中的 Anime、确认来源、最新
Source Snapshot 和 Airing Occurrence，输出平台无关的 `AnimeCardData`。

`AnimeCardData` 只包含经过安全过滤和格式化所需的值，不包含 ORM 对象、上游原始响应
或展示字符串。

### 7.2 `PosterCache`

Worker 在 Bangumi 或 AniList 快照同步后调用该接口。它只接收确认来源快照中的 HTTPS
图片 URL，在后台下载、校验并原子写入共享缓存。

海报优先采用 confirmed Bangumi 最新快照，其次采用 confirmed AniList 最新快照。
Bangumi 海报缺失或校验失败时，Worker 在同一后台任务中尝试 AniList；两个来源都不可用
时不写海报文件。

AstrBot 只通过 Anime ID 和内容摘要读取本地海报，不接收或访问远程 URL。

### 7.3 `AnimeCardRenderer`

输入 `AnimeCardData` 与已验证的本地海报路径，使用 Pillow 生成 `1000 × 600` PNG。
渲染器不查询数据库、不访问网络、不发送 QQ 消息。相同 Anime ID、投影快照版本、群
时区和下一集组成稳定的渲染缓存键。

### 7.4 `CardReplyFactory`

负责选择载体：

1. 场景属于搜索唯一命中、详情或下一集；
2. 本地真实海报存在且有效；
3. 本地卡片生成成功；
4. 返回图片 Reply 和一行提示。

任一条件不满足时返回等价文本 Reply。AstrBot 渲染层只把 Reply 映射为 Image 与 Plain
消息组件，不理解数据源投影规则。

## 8. 数据流

### 8.1 后台海报路径

```text
Worker 同步 Bangumi / AniList
        ↓
写入最新 Source Snapshot
        ↓
PosterCache 下载、限制、解码验证
        ↓
原子写入共享 card-assets 卷
```

### 8.2 群消息路径

```text
InteractionGateway 解析固定意图
        ↓
现有应用用例读取本地目录
        ↓
CardDataAssembler 读取本地投影与下一集
        ↓
PosterCache 只读本地真实海报
        ↓
AnimeCardRenderer 读取或生成本地 PNG
        ↓
CardReplyFactory 图片回复或等价文本
        ↓
SendGovernor → AstrBot → NapCat → QQ
```

群消息路径中的外部 HTTP 请求数必须为零。

## 9. 缓存与资源边界

Compose 新增命名卷 `card-assets`，同时挂载到 Worker 和 AstrBot 的固定路径
`/var/lib/anime-qqbot/cards`。Worker 写海报，AstrBot 写渲染缓存；双方使用临时文件加
原子 rename，不能读取半写文件。

缓存总上限默认 `300 MiB`。超过上限时由 Worker 按最近访问时间清理到 `270 MiB`，形成
回差，避免每轮反复删除。AstrBot 使用卡片时更新访问时间。缓存清理不得删除 PostgreSQL
目录、AstrBot 数据卷、NapCat 登录卷或项目其他文件。

渲染使用进程内单并发信号量。单张 `1000 × 600` RGBA 画布约 `2.3 MiB`，包括海报解码、
缩放和 PNG 编码后的验收新增峰值内存不得超过 `80 MiB`。不得启动浏览器进程。

后台海报下载采用以下安全限制：

- 只允许确认来源快照中的 HTTPS URL；
- 连接超时 `3 s`，总请求超时 `10 s`；
- 单文件最大 `8 MiB`；
- 只接受 JPEG、PNG 或 WebP；
- Pillow 解码验证成功后才进入缓存；
- 解码像素上限 `30 MP`；
- 文件名由 Anime ID 与内容摘要生成，不使用 URL 路径；
- 下载或校验失败只记录安全摘要，不记录 Token 或完整上游正文。

## 10. 错误与降级

| 错误 | 行为 |
| --- | --- |
| 没有海报 URL | 发送等价结构化文本 |
| 海报尚未后台缓存 | 发送等价结构化文本 |
| 海报下载或解码错误 | 删除坏临时文件，发送文本，等待 Worker 后续重试 |
| 海报尺寸异常但可解码 | 使用真实图模糊铺底并完整居中 |
| CJK 字体缺失 | 镜像构建失败，不发布 |
| Pillow 卡片渲染异常 | 记录安全摘要并立即发送文本 |
| 已渲染卡片缓存损坏 | 删除坏缓存，尝试一次本地重渲染；失败则发送文本 |
| QQ 图片发送结果未知 | 沿用现有 unknown 语义，不自动重复发送 |

不得生成或发送占位图。任何图片错误都不得影响搜索结果、候选会话、订阅状态或主动
通知任务。

## 11. 部署影响

应用镜像增加 Pillow 与固定 CJK 字体能力，不增加常驻服务。日常 ACR 发布仍只更新
Worker 与 AstrBot。Compose 新增共享卷会使这两个应用容器在首次实施发布时重建，但
NapCat 必须继续由现有发布隔离脚本保留。

发布前后继续记录 NapCat 容器 ID 与 `StartedAt`，要求：

```text
NapCat restart detected: no
```

本轮不修改 `napcat-qq`、`napcat-config`、`astrbot-data` 或 `postgres-data` 的数据语义。

## 12. 测试设计

### 12.1 单元测试

- 三个图片场景与所有文本场景的策略矩阵；
- `AnimeCardData` 的字段优先级、缺失字段、NSFW 与 disabled 拒绝；
- 群时区、星期、日期和集数格式；
- `1000 × 600` 输出、`400 × 600` 海报槽和固定视觉 Token；
- 标准、超宽、超高海报的等比处理；
- 无海报、坏海报和渲染异常只返回文本；
- 中文、日文、长标题与特殊字符；
- 渲染缓存键在快照、时区或下一集变化时失效；
- 300 MiB 上限与 270 MiB 清理目标；
- 下载大小、类型、像素、协议和安全文件名限制；
- 群消息路径不调用 HTTP 客户端。

### 12.2 集成与端到端测试

- Worker 把确认快照海报写入共享卷，AstrBot 可以读取；
- 临时下载文件只在验证后原子替换；
- 搜索唯一命中、详情、下一集产生图片 Reply；
- 搜索候选、列表、订阅确认、帮助和通知保持文本；
- 海报缺失、损坏或渲染失败时消息内容完整且没有 Image 组件；
- AstrBot Reply 正确映射为 Image 与一行 Plain 提示；
- 现有候选编号、防误触、限频、订阅和 Outbox 测试继续通过；
- Ruff、mypy 和全量 pytest 一次性通过。

### 12.3 真实镜像与服务器验收

- 构建实际 Docker 镜像并在容器内生成中日文样卡；
- 检查样卡尺寸、海报比例、文字边界和 PNG 可解码；
- 首次本地渲染不超过 `1 s`；
- 单并发渲染新增峰值内存不超过 `80 MiB`；
- 缓存超过测试阈值时按同一算法回收到 90%；
- 2 GiB Compose 覆盖下没有 OOM 或持续 swap 抖动；
- 日常发布只重启 Worker/AstrBot，NapCat 指纹不变；
- 手机 QQ 与桌面 QQ 中卡片均为普通横图大小，标题与时间可读。

QQ 测试群中的真实图片发送属于部署后的外部门禁，由部署者验证：

```text
搜番 <唯一命中名称>
@机器人 详情 <名称>
@机器人 下一集 <名称>
```

另选一个没有本地海报的条目，确认只收到结构化文本且没有占位图。

## 13. 完成标准

- 仅三个已确认场景在真实海报可用时发送放送信号卡片；
- 卡片固定 `1000 × 600`，左侧真实海报固定 `400 × 600`；
- 所有群消息请求不访问外部数据源或远程图片；
- 图片异常始终产生等价文本，不生成占位图；
- 缓存、内存和并发满足 2 GiB 服务器边界；
- 真实 Docker 镜像、自动化测试与静态检查通过；
- 应用发布不重启 NapCat；
- QQ 手机端与桌面端外部验收通过。
